# Software Supply Chain Policy

> Policy version: 1.0  
> Owner: Engineering / DevOps / Security  
> Last updated: 2026-05-09

## Purpose

Define controls for build integrity, artifact provenance, SBOM generation, dependency trust, and release artifact protection.

## Scope

Applies to packages, containers, build systems, CI/CD workflows, dependencies, artifacts, registries, provenance records, and release bundles.

## Mandatory Rules

- Builds must be reproducible or have deterministic inputs documented where practical.
- Release artifacts must be generated by approved CI/CD pipelines.
- Artifacts must be traceable to commit, build, and workflow run.
- SBOMs must be generated for production releases where applicable.
- Artifact integrity must be protected with checksums, signatures, or registry controls where possible.
- Build workflows must not use untrusted scripts without review.
- Dependencies must be pinned or locked where practical.
- Build systems must use least privilege.
- Production artifacts must not be manually modified after build.
- Provenance records must be retained.

## Required Checks

- SBOM generation
- Artifact checksum/signature verification
- Dependency lockfile review
- Build provenance record
- Registry access control
- CI/CD workflow review
- Container image scanning

## AI Agent Responsibilities

AI agents such as Claude, Codex, GitHub Copilot, ChatGPT, Gemini, or internal agents must follow these responsibilities:

- Generate SBOM and artifact metadata guidance
- Identify missing provenance
- Recommend safer dependency and build practices
- Do not alter released artifacts outside workflows
- Explain supply-chain findings

## Human Responsibilities

- Approve artifact generation process
- Review critical build workflow changes
- Validate artifact integrity
- Monitor registry access
- Maintain artifact retention

## Required Evidence and Artifacts

- Build logs
- Artifact manifest
- SBOM
- Provenance record
- Checksum/signature record
- Registry publish record
- Release tag

## Exceptions

Exceptions must be documented, time-bound, risk-assessed, approved by the required owner, and reviewed before expiration.

## Review Cadence

Quarterly, or after a major incident, failed deployment, audit finding, or significant process change.
